## Remaining limits and rollout requirements

- The R07 marker records the durable dispatch decision, not proof of a provider charge. Process interruption or an ambiguous network outcome after it commits is conservatively treated as started work if the user cancels. An ordinary terminal failure still uses the existing refund path.
- This is a local implementation handoff, not deployment approval. Apply the session-marker migration, align the deployed Stripe webhook API version, configure provider limits and test hosted billing before release.
- For R07, pause new generation admission and drain queued/running work with the old workers, apply the `paid_work_started_at` migration, and release the backend together with the Generate confirmation and website copy. A null marker on a job already running before deployment cannot establish whether its old worker made paid calls; do not blindly backfill or charge historical jobs.
- No live Stripe flow, paid provider/media quality sample, loaded extension on YouTube/Shorts/fullscreen, worker hard-kill/lease-expiry matrix, staging rollback, backup restore or scheduler/alert verification was run. The browser fixture uses actual UI code with fake transport; it does not prove extension/service-worker lifecycle behavior.

- PostgreSQL/Redis checks prove the tested lock/permit interleavings, not sustained production fairness, capacity or provider cost. Runtime queue counts are snapshots and external consumers must adapt to the explicit state fields.
- Unknown checkout outcomes intentionally block plan replacement and account deletion until safely reconciled. Failure refunds, deletion retention, already-admitted generation and relaxed lyrics-quality policies are preserved; voluntary cancellation now follows the user-approved September 16 rule.

How To Build Future Code

Build the smallest direct version that satisfies the current requirement.
Do not add bulk for imagined future cases. Make the current path clear,
typed, tested, and easy to delete or change later.

Core posture:
- Prefer one current product path over parallel old/new paths.
- Prefer loud failure over fake defaults or silent repair.
- Validate untrusted data at the boundary, then trust the normalized shape.
- Handle the real case directly instead of adding dodge flags.
- Remove dead code, obsolete comments, unused scaffold, and compatibility wrappers.
- Add abstractions only when they remove real repeated complexity.
- Keep helpers only when they name real domain behavior or have multiple call sites.
- Do not keep both implementations "for safety"; pick the correct one.
- Do not add fallbacks, retries, caches, polling, scoring, or provider indirection without evidence.
- Keep files and functions small enough to review in one sitting.

Backend rules:
- Request validation, provider responses, database records, and generated contracts are boundaries.
- After a boundary validates data, avoid repeating defensive shape checks downstream.
- Missing required provider configuration should fail before work starts.
- Provider output that violates the schema should fail with a stable public error.
- Persist only fields needed for product behavior, diagnostics, or retention.
- Keep routes API-only unless the product actually exposes server-rendered pages.
- Remove unused Laravel scaffold instead of carrying framework defaults.

Extension rules:
- Render only contract-valid state.
- Do not invent display fallbacks for unknown languages, timestamps, tracks, or tokens.
- If backend data is invalid, surface a clear failure instead of masking it in UI.
- Keep UI state transitions explicit and local to the workflow using them.
- Do not match cues by fuzzy text when timing or contract IDs define the current path.

Contract rules:
- Make required product inputs required in schemas.
- Do not make fields optional to preserve obsolete clients.
- Regenerate generated types whenever schemas change.
- Keep docs aligned with the current contract, not historical behavior.

Testing rules:
- Delete tests that preserve removed compatibility behavior.
- Add focused tests for each loud failure and each boundary validation.
- Tests should prove product behavior, not framework scaffold behavior.
- Prefer a small, readable fixture over a generic builder when only one case exists.

Documentation rules:
- Update durable docs when behavior, contracts, or validation expectations change.
- Keep docs short and operational.
- Do not document speculative paths that the code does not implement.

When unsure:
1. Ask whether the code protects a real boundary or a hypothetical problem.
2. If it is hypothetical, leave it out.
3. If a provider or client breaks the assumption later, add the narrowest fix with evidence.
